# VirtualTutor — Database & API Hooks Inventory (as of 2026-07-13)

Every integration point the program requires to run for real (persistent, multi-session, real
students), cross-referenced against what's actually wired up in `src/` today. Generated by reading
`prisma/schema.prisma`, `package.json`, and every service/domain file in `src/`, `DBEngines/`, and
`AccountConsentState/` directly — not from documentation claims.

**Headline fact, confirmed by direct grep and by 4 of the 8 audits in `AUDIT_EXPORT_2026-07-13.md`:**
`grep -rn "PrismaClient" src/` returns **zero hits**. The program currently runs entirely on
in-memory `Map`s standing in for the database. Nothing in this repo talks to a real database or
cache at runtime yet — only the Anthropic API is actually called.

## 1. External API hooks

| Hook | Where | Status | Notes |
|---|---|---|---|
| **Anthropic Claude Messages API** (`@anthropic-ai/sdk` v0.105.0) | `src/main.ts:114,229-239` | **Live — the only real external call in the codebase** | `anthropic.messages.stream({ model: "claude-haiku-4-5-20251001", max_tokens: 512, system, messages })`. Streamed token-by-token straight to `process.stdout` before any validation runs (see `f9efff1f` in the audit export). No `AbortController`/timeout, no retry/circuit-breaker (see `6abb4eb7`). Model ID is hardcoded, not configurable. |

`ANTHROPIC_API_KEY` is read from `.env` (`src/main.ts:105`) and is the only required secret for the
program to run today.

No other external API is called anywhere in `src/`, `DBEngines/`, or `AccountConsentState/` — no
REST framework (Express/Fastify/etc.), no HTTP server is stood up at all. The program is a
single-process terminal REPL (`npx tsx src/main.ts`); there is currently no way for an external
client to call into this program over the network.

## 2. Database hooks (Postgres via Prisma)

**Declared but not wired.** `prisma/schema.prisma` defines 8 models + 4 enums. `DATABASE_URL` is
present in `.env`. `@prisma/client` and `@prisma/adapter-pg` are installed dependencies. But there
is no `new PrismaClient()` anywhere in `src/`, and `npx prisma migrate dev` has never been run
against a live database (confirmed in `src/HANDOFF.md` §"Notes for the implementer" — schema is
`prisma validate`-clean but unmigrated).

| Model | Purpose | Required by | Current runtime substitute |
|---|---|---|---|
| `User` | Auth identity (email + password hash) | `AccountService.createAccount`/`getAccount` (stub, not implemented) | None — `AccountService` methods are all `// TODO: implement` and return hardcoded empty/null values (`src/services/AccountService.ts`) |
| `Student` | 1:1 with `User`; owns `profile_status`, `active_session_id`, `session_count` | `AccountBase.canStartSession()` (defined, never called — see audit `f3ed828a`) | None |
| `LearningProfile` | 1:1 with `Student`; `cognitive`/`behavioral`/`historical` JSONB + `profile_version` (optimistic-lock column) | `ProfileService.getProfile`/`buildInitialProfile`/`applyProfilePatch` | `ProfileService.profilesByStudentId: Map<string, LearningProfileStore>` (`src/services/ProfileService.ts:34`) |
| `Session` | `active → ended → finalized`/`error` lifecycle, `profile_version_at_start` | `SessionService.startSession`/`endSession` | `SessionService.sessionsById: Map<string, Session>` (`src/services/SessionService.ts:20`) |
| `SessionEvent` | Append-only per-turn log (`seq`, `role`, `content`, `profile_version_at_turn`) | `SessionService.appendEvent`/`getSessionEvents` | `SessionService.eventsBySessionId: Map<string, SessionEvent[]>` (`src/services/SessionService.ts:22`) — unbounded, no eviction (flagged by audits `f9efff1f`, `6abb4eb7`) |
| `ProfilePatch` | End-of-session diff (`operations: Json`, `base_profile_version`/`new_profile_version`, unused `review_flags` column) | `FinalizerService.finalizeSessionToPatch`/`applyPatchCompareAndSwap` | In-memory `ProfilePatch` object applied directly to the in-memory `LearningProfileStore`; CAS check is pure JS (`patch.baseProfileVersion !== store.profileVersion`), no `WHERE profile_version = $1` SQL guard (flagged by audits `83d5a1fe`, `f3ed828a`) |
| `IntakeQuiz` | Onboarding quiz responses (`raw_responses: Json`, `rag_output`, `processing_status`) | `ProfileService.buildInitialProfile(quiz)` | Constructed inline in `main.ts:125-130` with a hardcoded `student_id: "demo-student-001"` — never persisted |
| `SystemErrorLog` | Error tracking (`error_component`, `error_details`, `is_resolved`) | Not called from anywhere | Fully unused — no code path writes to this model's shape at all |

**Fields referenced in older design docs (`firstDocument.md`) that do NOT exist in the schema or
codebase** (confirmed by audit `83d5a1fe` — do not assume these are implemented anywhere):
`KCMasteryEntry`, `FrictionEntry`, `mathAnxietyIndicators`, `commonErrors`, `frictionMap`. KC state
instead lives nested two levels deep inside `LearningProfile.cognitive` JSONB
(`SkillState.knowledgeComponents: Record<string, KCState>`) — see `src/domain/profile/
LearningProfileStore.ts`.

**Required but not yet modeled anywhere:** a `KCPrerequisite`-style edge table. The current
`checkPrerequisiteGate(skillId)` (`LearningProfileStore.ts:271-276`) checks a skill's own mastery
against the 0.75 threshold, not a *different* foundational skill's mastery — there is no
prerequisite-dependency data in the schema or codebase to check against even if the method were
fixed.

## 3. Cache/session hooks (Redis)

| Hook | Where | Status |
|---|---|---|
| `RedisSessionCache` (`ioredis`-backed) | `src/db/redis/RedisSessionCache.ts` | **Implemented, but never imported or instantiated anywhere in `src/main.ts` or any service.** Full CRUD is written: `setSession`/`getSession`/`refreshTTL`/`deleteSession`, keyed `session:{studentId}`, 4-hour TTL (14400s), intended to hold the live per-turn `ConversationHistory` buffer and be explicitly `DEL`'d by `FinalizerService` on session close (per its own header comment) rather than waiting on TTL. |
| `DBEngines/Redis/base.ts` | Design-note stub | Comment-only file (7 lines) — the original design spec that `RedisSessionCache.ts` was written to satisfy. Not executable, not imported anywhere. |

**What actually holds conversation state today instead of Redis:** `main.ts`'s local
`recentExchangeLines: string[]` array (`main.ts:139`), capped to the last 6 lines per prompt via
`.slice(-6)` but never capped in the buffer itself between failed attempts (flagged by audit
`6abb4eb7`). This is a stack variable in the REPL process — it disappears entirely on crash/SIGINT
and was never intended to be the durable session buffer per the architecture described in
`src/HANDOFF.md`.

`AccountConsentState/LRUCache.ts` — a **design-note-only** file (10 lines of comments) describing a
future `ActiveSessionLRUCache` (bounded-capacity active-session eviction). Explicitly marked
out-of-scope/TODO in `RedisSessionCache.ts`'s own header comment. Not implemented.

## 6. Summary — what's real vs. what's scaffolded

**Actually wired and executing on every run:**
- Anthropic Claude Messages API (streaming), via `ANTHROPIC_API_KEY`.

**Fully specified (typed, tested in isolation) but backed by in-memory stand-ins, not real
persistence:**
- `ProfileService` (Prisma `LearningProfile` → `Map`)
- `SessionService` (Prisma `Session`/`SessionEvent` → `Map`s)
- `FinalizerService` (Prisma `ProfilePatch` write/CAS → direct in-memory mutation)

**Implemented as a real class but never invoked from the actual runtime path:**
- `RedisSessionCache` (`ioredis`) — dead code today; `main.ts` uses a local array instead.

**Pure stubs — signature + TODO comments only, no logic:**
- `AccountService` (all 4 methods)
- `AccountBase.canStartSession()` — implemented, but its *caller* is missing, not the method itself.

**Legacy/reference-only — explicitly not part of the live system per `src/HANDOFF.md`:**
- `AccountConsentState/*`, `LearningProfile/` (top-level dir), `DBEngines/`, `Auth/`,
  `PromptEngine/`, `models.ts`.

Any prioritization of "what to build next" should treat wiring `PrismaClient` into `ProfileService`/
`SessionService`/`FinalizerService` (with the DB-level CAS guard described in
`AUDIT_EXPORT_2026-07-13.md`'s `83d5a1fe`/`f3ed828a` findings) as the single change that would make
the largest number of other audit findings in that file load-bearing rather than theoretical.
